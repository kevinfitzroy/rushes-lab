## 2. P0 缺陷

### F1 — 盲搜 endpoint 每次请求 500(`routers/assets.py:289-291`,PR #157)

```python
lbl = func.unnest(Asset.user_labels).alias("lbl")
label_fuzzy = exists(
    select(1).select_from(lbl).where(next(iter(lbl.c)).ilike(pattern, escape="\\"))
)
```

SQLAlchemy 把它渲染成:

```sql
EXISTS (SELECT 1 FROM unnest(assets.user_labels) AS lbl WHERE lbl.unnest_1 ILIKE '%vip%')
```

PostgreSQL 里 `FROM unnest(arr) AS lbl` 的输出列名是 `lbl`(别名),不是 `unnest_1` 也不是 `unnest`。**server2 PG16 实测**:

```
=== A: lbl.unnest_1 (SQLAlchemy 实际发出的) ===
ERROR:  column lbl.unnest_1 does not exist
=== B: bare lbl (别名) ===  → count 0   ✅
=== C: lbl.unnest ===        → ERROR:  column lbl.unnest does not exist
```

`label_fuzzy` 是 `or_()` 的一个分支,**无条件参与每一次查询** → 整条 SQL 抛 `ProgrammingError` → endpoint 500。前端 `useSearchAssets` 每次搜索都会弹"数据加载失败"。

**为什么漏了**:`tests/test_search_labels.py` 有 4 条会打到这个 endpoint 的用例(`test_tag_then_search_hit_by_label` / `test_search_hit_by_notes_and_filename` / `test_search_sensitive_zero_leak_for_outsider` / `test_search_evan_sees_sensitive`),一跑就红 —— 但实施机无 docker,一次没跑。

**修法 A(最小改动,已实测编译正确)**:

```python
lbl = func.unnest(Asset.user_labels).table_valued("label").render_derived(with_types=False)
label_fuzzy = exists(select(1).select_from(lbl).where(lbl.c.label.ilike(pattern, escape="\\")))
# → EXISTS (SELECT 1 FROM unnest(assets.user_labels) AS anon_1(label) WHERE anon_1.label ILIKE ...)
```

**修法 B(推荐,顺带解决 F8 索引失效)**:

```python
label_fuzzy = func.array_to_string(Asset.user_labels, " ").ilike(pattern, escape="\\")
```
配一个表达式索引 `CREATE INDEX ... USING gin (array_to_string(user_labels,' ') gin_trgm_ops)`。既正确又可索引,还省掉 lateral。

### F2 — 管理后台建的账号登录不了(`services/local_auth.py:112-128`,PR #158 × #160 交叉缝)

`find_user_by_username()` 的匹配规则:

```python
if "@" in lowered:  stmt = select(User).where(func.lower(User.email) == lowered)
else:               stmt = select(User).where(func.lower(User.name)  == lowered)
```

**`users.username` 从头到尾没参与登录匹配。** 而 `username` 恰恰是 #150 为本地登录新建的列,三处 UI/契约都把它称作登录名:

- `routers/directory.py:57` `UserCreateIn.username` — `description="登录名:拼音/工号友好,不强制邮箱格式"`
- `web/src/pages/AdminUsersPage.tsx:254` — 表单 label **「登录名(拼音 / 工号,登录用)」**,extra「提交后不可改;本地用户无飞书身份,登录名是唯一标识」
- `web/src/pages/LoginPage.tsx:93` — 输入框 placeholder「工号 / 拼音用户名 / 邮箱」

实际行为:admin 建 `username=zhangsan` / `name=张三` / `email=None` 的账号 → 用户按 UI 提示输 `zhangsan` → 401「用户名或密码错误」。唯一能登进去的输入是显示名「张三」。

**次生风险**:`users.name` 没有唯一约束,`create_directory_user` 也只查 `username` 重复。两个员工重名(医美行业常见)→ `find_user_by_username` 命中 2 行 → 返回 `None` → **两人都永久登录不了**,且日志只有一行 `login username ambiguous`。

**为什么漏了**:`tests/test_local_auth_integration.py` 的 `make_user` fixture 只写 `name` / `email`,从不设 `username`;`test_directory.py` 只测 CRUD,没有"建号 → 登录"的贯通用例。#149 先合(10:47),#150 后合(10:47),两边各自绿。

**修法**:

```python
# 优先级:username 精确 → email(含 @)→ name(兜底,保留老飞书用户可登)
stmt = select(User).where(func.lower(User.username) == lowered).limit(2)
# miss 再按 email / name 回退
```
并在 `create_directory_user` 里对 `name` 重复给出提示(不必硬拦,但要让 admin 知道会影响 name 兜底登录)。
补一条端到端用例:`POST /admin/directory/users` → `POST /auth/local/login`(用返回的 username + temporary_password)→ 200。

## 3. P1 缺陷

### F3 — `username` / `oidc_sub` 的 UNIQUE 只存在于 ORM,不在数据库里

migration 0008 / 0010:

```python
op.add_column("users", sa.Column("username", sa.String(64), unique=True, nullable=True))
op.add_column("users", sa.Column("oidc_sub", sa.String(255), unique=True, nullable=True))
```

Alembic 的 `add_column` 不会发出 UNIQUE。**本机实测编译结果**:

```
AddColumn DDL: ALTER TABLE users ADD COLUMN username VARCHAR(64)
```

随后建的 `ix_users_username` / `ix_users_oidc_sub` 都是**普通 btree**,不是 unique index。对比:`groups.name` 走的是 `create_table`,`unique=True` 在建表时会正常渲染 —— 所以只有这两列受影响。

后果:
- `create_directory_user` 的重复检查是"先 SELECT 再 INSERT",并发下可产生同名 username;
- OIDC 留口启用后,`upsert_user_from_userinfo` 用 `scalar_one_or_none()` 按 `oidc_sub` 查,一旦有重复行会抛 `MultipleResultsFound` → 登录 500。

`tests/test_db_schema.py:59` 断言的是 `User.__table__.c.username.unique is True`(ORM 元数据),**天然抓不到数据库层缺失** —— 假绿。

**修法**:补一个 migration `op.create_unique_constraint("uq_users_username", "users", ["username"])`(+ `oidc_sub`),或把两个 index 改成 `unique=True`。顺手把 schema 测试改成对 live DB 查 `pg_indexes`(容器测试里做)。

### F4 — `backup_prod.sh --mirror` 直接 usage 退出(PR #159)

```bash
MODE="${1:-pg}"
[[ "$MODE" == "--all" ]] && MODE="all"       # 只归一化了 --all
if [[ "$MODE" != "pg" && "$MODE" != "mirror" && "$MODE" != "all" ]]; then ... exit 1; fi
```

`--mirror` 没有被翻译成 `mirror` → 落进 usage 分支 exit 1(已本地复现)。而 ops-manual §10.5 的 cron 示例正是:

```
30 3 * * 0  cd /root/material-storage-api && bash scripts/backup_prod.sh --mirror >> /var/log/ms-backup.log 2>&1
```

即**原片周备永远不会执行**,只有每日 pg_dump 生效。考虑到 ROADMAP 把"当前代码无任何备份机制"列为 P0 生产缺口,这条要在内网首装前修掉。

顺带两点:
- **`ms-thumbs` 不在任何备份路径里**。脚本注释「MINIO_MIRROR_BUCKET 默认 ms-dev(含历史缩略图一并备份)」只对 ADR-0008 之前的布局成立;分层之后缩略图在独立实例的独立 bucket 上。缩略图可从原片重生成,不算数据丢失,但 ADR-0008「备份与分层对齐」这条实际没落地,应在 ops-manual 写明"缩略图不备份,靠 backfill 重建"(且见 F14 —— backfill 现在重建不了)。
- `mc alias set` 把 access/secret 作为命令行参数传进容器,host 上 `ps` 短暂可见。脚本注释说"不打印值",实际进程参数会带。低危,但内网多人运维时值得改成 env 注入。

### F5 — 禁用用户不下线(ADR-0007「离职 = 手动禁用 + 审计兜底」)

`deps.py:79-89` 的 `get_current_user` 纯解 JWT,不查库;#149 把 `session_jwt_ttl_seconds` 设为 **7 天**。`disable_directory_user` 做了两件事:撤全部 OpenFGA tuple + `is_active=false` —— 但**不影响已签发的 cookie**。

在 tuple 被撤掉之后仍然可达的面:
- `GET /assets/{id}/thumbnail-url` —— 只要求登录,**不做任何 OpenFGA 判定**(既有决策:缩略图不过 enforce),被禁用的人仍可按 asset id 拉任意缩略图;
- `POST /auth/change-password`、`GET /notifications`、`GET /auth/me` 均照常。

ADR-0007 把"离职自动回收"降级、改成手动禁用是业务拍板的,没问题;但既然手动禁用是**唯一**闭环,它必须真的立即生效。

**修法**(择一):`get_current_user` 加一次轻量 `is_active` 校验(Redis 缓存 30s,成本可忽略);或 disable 时写 session 黑名单;或 JWT 里带 `token_version`,disable 时 bump。

### F6 — 禁用 → 启用会静默丢掉用户组权限(PR #160)

- `disable` → `revoke_user_completely()`,其 `USER_DIRECT_RELATIONS` 含 `("group","member")` → group tuple 被删;
- `enable` 只调 `add_user_to_organization()`,**没有按 `group_memberships` 重建 group tuple**;
- 而 `group_memberships` 表行在 disable 时并没有删。

净效果:重新启用后,`GET /admin/directory/groups/{id}/members` 照样把这个人列为组成员(读的是 DB),但 OpenFGA 里没有 tuple → 组带来的项目权限全部失效,且没有任何提示。管理后台的显示与真值不一致,排查时很难想到。

**修法**:`enable` 里按 `select(GroupMembership).where(user_id==...)` 逐条 `add_user_to_group`;或 disable 时一并删 DB 行(那就得接受"启用后要重新加组"的语义,需在 UI 写清)。

### F7 — subject 迁移脚本:验收信号必然误报 + 部门轴权限断崖(`scripts/migrate_subjects_to_uuid.py`,#148)

这个脚本还没在 server2 跑过(handoff §2.4-1),cutover 时才会用到,有两个问题:

1. **before 快照对本地用户恒空**。`_snapshot(..., subject_fmt="user:{open_id}")` 对 `feishu_open_id IS NULL` 的本地账号会拼出字面量 `user:None` → before 恒为空集,after 有值 → `equal=False` → `consistency_ok=False` → **退出码 4**。#150 之后本地账号必然存在,所以这个"迁移前后一致"的验收信号**必然是红的**,运维会分不清是真回归还是噪声。
   修法:快照时跳过 `feishu_open_id IS NULL` 的用户(它们本来就已经是新格式)。

2. **department 轴的权限断崖没有被处理,而脚本自称一致**。所有 `department:` 相关 tuple(包括 `user:<open_id> member department:X`)一律 skip、原样保留旧 subject。迁移后 `user:<UUID>` 不再是任何部门的 member → **所有通过 `department:X#member` 拿到的 project viewer/downloader 直接消失**。
   这个结果本身符合 ADR-0007「砍掉部门轴」,但它和文件顶部写的"验收:代表性用户迁移前后 list_objects 结果一致"是直接矛盾的。cutover 前必须先做一步:把现存的部门授权物化成本地组或用户直授,再跑迁移。判断存量影响**一律查 OpenFGA store**(ROADMAP 已有此告诫)。

3. 小问题:重写计划里的本地组 id 用 `uuid5` 确定性算出,而 `_ensure_local_group` 在"同名已存在"时会返回**另一个** id(`by_name.id`)→ 写出的 tuple 指向一个不存在的 group 行。概率低(name 是裸飞书 gid),但值得对齐。

### R1(P0)— migration 0011 的表达式索引根本创建不了,`alembic upgrade head` 必失败

```python
op.create_index(..., [sa.literal_column("array_to_string(user_labels, ' ')")], postgresql_using="gin", ...)
```

PG 里 `array_to_string(anyarray, text)` 是 **STABLE**(`provolatile='s'`),不能进索引表达式。server2 PG16 实测:

```
ERROR:  functions in index expression must be marked IMMUTABLE
```

后果比 F1 本身更靠前:**任何全新数据库都过不了 `alembic upgrade head`**,ms-api 起不来、deploy 脚本的 migrate 步骤直接红 —— 正好挡住"本地/内网跑起来"这件事。

**修法(本次已实施,server2 PG16 实测通过)**:用 IMMUTABLE SQL 包装函数落地,这是 PG 社区的标准做法;查询侧同步改成同一个函数,否则表达式不一致索引不会命中。

```sql
CREATE OR REPLACE FUNCTION ms_labels_text(labels character varying[])
RETURNS text LANGUAGE sql IMMUTABLE STRICT PARALLEL SAFE
AS $$ SELECT array_to_string(labels, ' ') $$;

CREATE INDEX ix_asset_user_labels_str_trgm ON assets
  USING gin (ms_labels_text(user_labels) gin_trgm_ops);
```

实测执行计划(`SET enable_seqscan=off`):

```
Bitmap Heap Scan on assets
  ->  Bitmap Index Scan on ix_asset_user_labels_str_trgm
        Index Cond: (ms_labels_text(user_labels) ~~* '%vip%'::text)
```

顺带把 `label_exact`(`q = ANY(user_labels)`)删掉:拼串 ILIKE 是它的超集(标签必然是拼串的子串),留着既冗余、又因为不走 GIN `array_ops` 而把整个 `OR` 拖回全表扫 —— F8 到这里才算真正闭合。

> 直接改已 merge 的 0011 而不是叠一个 0012:0011 从没在任何环境成功执行过(server2 停在 0006,实施机无 docker),就地修正比留一个永远失败的 revision 干净。

### R2(P0,新发现)— macOS 上 `uv sync` 装不出 greenlet,异步 DB 代码根本跑不了

`sqlalchemy>=2.0` 不带 `[asyncio]` extra 时,greenlet 只在 `platform_machine` 命中 x86_64/aarch64 等值时才是硬依赖 —— **linux 容器里自动有,macOS arm64 上没有**。表现:#167 新加的 `TestFindUserByUsername`(6 条)在干净 `uv sync` 后全部 setup 报错:

```
ValueError: the greenlet library is required to use this function.
```

也就是说这 6 条新测试在实施机上一次没绿过。修法:依赖声明改 `sqlalchemy[asyncio]>=2.0`。装上后本机 57 → 61 passed。

顺带把 `httpx[socks]` 加进 dev 组:本机 shell 有 `ALL_PROXY` 时 `httpx.AsyncClient()` 会走 SOCKS,`tests/test_oidc_service.py` 的 4 条会 `ImportError: ... socksio ...` —— 就是 handoff §2.3 记的"~16 个 socksio 环境预存 errors",装上即消,不必再当噪声记着。

### R3(P2)— 强制改密拦截让每个请求多开一次 session

#168 的 `get_current_user` 先 `_load_active_user()` 开一次 session 查 `is_active`,再为 F15 开第二次 session `db.get(User, uid)` 查 `must_change_password`。缩略图这类高频端点(一屏 100 个格子 = 100 次请求)会被放大成 200 次查询。已合并成一次 `select(id, name, is_active, must_change_password, password_hash)`,行为不变。

### R4(P2)— `test_temp_password_has_both_cases_and_digits` 的 flaky 是生成器的问题

handoff 把它记成"基线 flaky、非本阶段引入",但根因是 `generate_temp_password` 纯随机采样:12 位缺数字的概率 `(48/56)^12 ≈ 16%`,和实测 1/5 吻合。而 `validate_password_policy` 要求字母 + 数字 —— 也就是说**管理员发出去的临时密码有 1/6 概率不满足系统自己的密码策略**。已改成大写/小写/数字各保底一个再洗牌,连跑 8 次全绿。
