# 调研:去飞书化的身份体系选型(自建账号 / 通用 OIDC / 自托管 IdP)

> **调研日期:** 2026-08-09
> **版本:** v0.3(调研,非决策;最终选型需业务同事输入后走 ADR 流程,可能 amend/supersede [ADR-0002](../decisions/0002-feishu-contacts-as-identity-source.md) 的"飞书通讯录作 SoT"路线。**v0.2:** 深挖权限模型 v4 后重写 §3 —— 撤回"subject 迁移可先行"建议。**v0.3:** 业务输入到齐(2026-08-09:飞书非日常 IM、实际用企业微信、离职闭环降优先级)→ 结论收敛为**放弃飞书(含 connector),S1 自建 + OIDC 留口**,决策载体 [ADR-0007](../decisions/0007-drop-feishu-self-built-identity.md)(accepted))
> **驱动背景:** 生产环境确定改为**局域网部署**(2026-08)。飞书集成在内网的受限面已盘点完毕(§1 附摘要);管理层提出疑问:"飞书集成带来的不一定是方便;不用飞书用户体系、换一个普通的 OAuth + 应用内按需自建管理体系,是不是更简单?"
> **结论摘要(TL;DR):**
> - **"换一个普通 OAuth 更简单"只在一种情况下成立:客户已经有现成的 IdP(AD/LDAP/Keycloak/IDaaS)。** OAuth/OIDC 是联邦登录协议,**不是用户目录** —— 没有 IdP 时,"接标准 OAuth"的前提是先运维一个 IdP,运维地板(ops floor)反而高于自建。
> - **对"单应用 + 几十~几百用户 + 局域网"的形态,社区共识与本文分析一致:应用内自建账号体系是最简路径**(见 §6 证据)。**(v0.3)业务输入到齐后结论收敛:放弃飞书(含 connector),终态 = 本地账号 + 应用内管理 + 标准 OIDC 留口**(§7;决策载体 ADR-0007)。
> - **飞书集成真正的业务价值不是"登录方便",是两条:① 离职自动回收权限(顾客隐私数据的合规闭环);② 审批/分享通知的 IM 触达。** 这两条的去留是业务问题,不是技术问题 —— §8 列了需要业务同事回答的问题清单。
> - **(v0.2 修正)subject 迁移不是可先行启动的"保险步骤",而是去飞书化决策的下游实现细节。** 深挖权限模型 v4 后确认:OpenFGA model 本身不耦合飞书(耦合的是 tuple 数据与调用点);"只迁 user subject"的半迁移零收益;坚持飞书认证则无需任何迁移;混合路线可增量引入本地 subject 空间、不动存量 tuple(§3)。

## 1. 为什么重新评估:内网部署下飞书集成的受限面(已核实摘要)

2026-08-08 会话已完成一轮代码 + 飞书官方规则核实,结论浓缩如下(详细证据见会话记录;此处只留决策相关的事实):

| 能力 | 内网可行性 | 依据 |
| --- | --- | --- |
| 飞书 OAuth 登录(redirect 回内网地址) | ✅ 可行 | (官方/社区)重定向 URL 允许 `http://内网IP:端口`,配置时不做可达性校验、无 ICP 要求;redirect 由**用户浏览器**完成,飞书服务器不回访 |
| 出站 API(token / 通讯录拉取 / 发 IM 卡片) | ✅ 可行 | (代码 `services/feishu_client.py`)纯出站 HTTPS,唯一前提是服务器能出站到 `open.feishu.cn:443` |
| 事件订阅(通讯录变更 / 离职 / 卡片回调) | ⚠️ 公网 webhook 必挂;官方**长连接(WebSocket)模式**可替代,纯出站 | (官方)长连接仅自建应用可用、不支持代理;`card.action.trigger` 官方明确支持;**通讯录事件走长连接官方无逐事件清单,需 POC 实测** |
| 飞书客户端内嵌能力(网页应用/JSAPI/可信域名) | ❌ 内网不可用,但纯浏览器使用本来就不需要 | (官方)该体系只对跑在飞书客户端内的网页有意义 |
| 换同类平台(钉钉/企业微信) | 钉钉同飞书口径(可内网 IP 回调);**企业微信强制可信域名、明文不支持 IP、需归属验证,纯内网不可用** | (官方/社区)企微服务商帮助文档 |

**关键推论:** 内网部署本身**不构成**必须放弃飞书的理由(长连接 + 出站 API + redirect 规则都走得通)。重新评估的真正理由是本文的正题:**飞书集成对这个产品的投入产出比,以及业务上是否真的依赖它。**

## 2. 飞书集成今天到底给了我们什么(价值盘点)

按"业务的谁、在什么频率、得到什么"盘点,而非按功能清单盘点:

### 2.1 身份侧(用户体系)

| 能力 | 代码位置 | 业务价值 | 没了它会怎样 |
| --- | --- | --- | --- |
| 扫码/账号登录,免注册免记密码 | `routers/auth.py`、`services/auth.py` | 员工上手零成本;无密码可泄露 | 需要一套本地账号(含密码策略/重置流程),管理员要开户 |

| 能力 | 代码位置 | 业务价值 | 没了它会怎样 |
| --- | --- | --- | --- |

### 2.3 代价侧(常被忽略)

- (代码)**身份深度耦合**:OpenFGA subject 一律是 `user:<feishu_open_id>` / `group:<gid>#member` / `department:<dept_id>#member`(见 `services/permissions.py` `fmt_subject`),权限数据的每一行 tuple 都引用飞书 ID —— 这是换用户体系时唯一真正贵的点(§3)。
- (代码)GroupPicker 实时调飞书通讯录 API(`routers/groups.py:44`),选组体验依赖飞书在线。
- 运维面:飞书应用要维护版本发布(改权限/事件配置后必须发布才生效)、凭据轮换、平台规则跟踪;内网场景还要加长连接进程。
- 业务前提:**客户组织的入转调离真的跑在飞书上**。如果飞书只是"装了但没人用",2.1 的自动同步价值归零,只剩一个登录按钮。

## 3. 耦合面盘点与"subject 迁移"再评估(v0.2 全节重写)

### 3.1 当初为什么用飞书 ID 作 subject(原始决策依据)

飞书 ID 直作 OpenFGA subject 是 **v3→v4 的刻意改动**(`permissions-model-v4.md` 头部:"v3 (PoC) → v4(生产路径,飞书 ID 直作 OpenFGA subject)"),依据记录在该文 §3:

- 飞书事件直接带 `open_id`,转换 UUID 又要查 db,徒增延迟 + 单点
- 管理员在飞书后台改组织,事件流直接更新 OpenFGA,无需中转

ADR-0002 同时做了**分层对冲**:users 表 PK = 内部 UUID(与飞书 ID 解耦,原文注明"便于未来更换 IM"),`feishu_open_id` + `union_id` 作稳定外键;权限层则直用飞书 ID。即"数据库层解耦、权限层直用"是权衡后的刻意分层,不是疏漏。

### 3.2 耦合面的真实形状(v0.2 代码核实)

- **OpenFGA model 零耦合**:`store.fga.yaml` 里 `type user` 是不透明字符串,无任何飞书特有构造 —— "迁移"不存在 model 改动,只存在 **tuple 数据迁移 + 调用点改写**。
- 耦合在数据与调用点:`open_id` 在 `api/app/` 出现 458 处 / 29 文件;`permissions.py` 低层接口本就接受 raw subject string(model-agnostic),飞书形态全部由调用方经 `fmt_subject()` 构造。
- 关键结构性事实:**只要组织架构还活在飞书,`department:<dept_id>` / `group:<gid>` 两类 subject 就必然是飞书 ID**(部门嵌套 tuple 由飞书事件直接灌入,`permissions-model-v4.md` §8)。

### 3.3 结论:坚持飞书认证 → 不迁;迁移是"去飞书化"的下游实现细节

v0.1 曾建议"subject → UUID 作为任何选型共同的 P0、不等业务结论先行启动",**v0.2 撤回**。理由:

1. **半迁移零收益。** 只迁 `user:` 到 UUID 而 group/department 留在飞书 ID = 混合制:每次 check 多一次 open_id→UUID 解析、所有事件 handler 加解析层,而 store 里仍全是飞书 ID —— 解耦收益为零,v4 的两条设计收益(事件流直写、免中转)全丢。
2. **全迁移 = 自建工程本身。** group/department 一并本地化意味着本地目录管理(组/部门 CRUD + 成员维护),那正是 S1 的主体工作量,不可能作为"保险"先行。
3. **混合路线不需要迁存量。** subject 是字符串,`ou_` 前缀 open_id 与 UUID 天然不冲突;未来引入本地账号时,新用户直接用 `user:<uuid>` 作 subject、存量 feishu tuple 一字不动(`CurrentUser` 本就同时携带 UUID 与 open_id,调用点按需选择)—— 增量采用,无迁移。
4. **坚持飞书 → 什么都不用动**,并继续享受 v4 设计收益:离职事件 payload 直接驱动 `revoke_user_completely(open_id)`(`permissions.py:334`);本地 DB 重建/重 seed 不悬空 tuple(open_id 外部稳定);OpenFGA store 可直接对照飞书后台人肉审计。

**留在飞书 subject 上的真实尾部风险(知情接受):** `open_id` 是应用域 ID —— 更换飞书租户 / 重建应用时 open_id 全变,user tuple 全悬空,需以 `union_id` 为 join key 跑 remap 脚本补救(ADR-0002 存 union_id 正是此对冲)。概率低、有补救路径,坚持飞书路线即视为接受。

**各终态下的迁移动作对照:**

| 终态 | subject 迁移动作 |
| --- | --- |
| 坚持飞书(S0) | 无 |
| 混合(S5) | 不迁存量;新增本地用户/组用 UUID subject 空间,与 `ou_` 前缀共存 |
| 彻底自建(S1) | 全量迁(user/group/department → 本地主键):读 tuple → open_id→UUID 映射重写;单租户数据量为脚本级工作量,作为 S1 工程子任务,不单列 |

## 4. 候选方案

### S1. 应用内自建账号体系(本地账号密码 + 管理后台)

**构成:**
1. 本地登录:账号 + 密码(argon2/bcrypt 哈希,新增一个依赖),签发**现有同款 session JWT**(session 机制零改动);登录失败限流、密码策略、首次登录强制改密。
2. 管理后台:用户 CRUD / 禁用(= 离职)/ 密码重置;本地用户组 CRUD 与成员管理 —— 成员变更直接写 OpenFGA tuple(接管原 `contact_sync` 的角色,但数据流从"拉飞书"变"本地编辑",代码反而更少)。
3. 组织架构简化:**砍掉部门轴,只留组**(推断:百人级单租户,部门树是飞书同步的副产品,不是业务刚需;权限模型 v4 的三轴 viewer/downloader/uploader 与组正交,不受影响)。此点若业务不同意,管理后台加一个简单部门字段即可,不改变架构。
4. 审计:`audit_events` 体系已存在,管理操作照现有 `audit.write()` 惯例接入。

**工作量粗估:** 身份解耦(中)+ 本地认证(小~中)+ 用户/组管理 UI(中)。**总计是三个候选里唯一"完全自己掌控、无新增运维组件"的路线。**
**风险:** 密码安全责任自负(哈希、限流、重置流程);离职回收从"自动"变"管理员手动 + 审计兜底"(§8 问题 3)。

### S2. 通用 OIDC 对接客户既有 IdP

应用实现标准 OIDC RP(authlib 已在依赖里,`services/auth.py` 的飞书 OIDC 流程本身就是标准授权码流程的飞书方言,抽象一层 provider 配置即可),对接客户已有的 AD/LDAP(经 ADFS/Keycloak 桥)/ Keycloak / 商业 IDaaS。

**判断:这是"普通 OAuth 更简单"唯一成立的情形 —— 简单的前提是 IdP 已经存在且有人管。** 需要先向客户确认有没有(§8 问题 5)。工作量:小~中(抽象 provider + claim 映射 + 组映射)。注意组/组织架构映射各 IdP 方言不同(groups claim、LDAP memberOf),通常只能拿到组名列表,精细权限仍建议落在应用内组。

### S3. 自托管开源 IdP(客户没有 IdP,但想要"标准 OAuth")

事实核实(2026-08,来源见各条;star 为 GitHub 实时量级):

| 产品 | 许可证 | 管理 UI | OIDC Provider | LDAP | 部署形态 | 社区 | 坑 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **Keycloak** | Apache-2.0(CNCF Incubating) | ✅ 完整 Admin Console | ✅(OIDC+SAML) | 可作源,非服务端 | Java/Quarkus + DB,镜像 600MB+,空载内存 512MB 起 | ~35k ⭐ | 概念陡、升级路径复杂;(社区)对单小应用属"运维地板"超标 |
| **authentik** | MIT 核心 + EE 拆分(source-available) | ✅ 完整 + flow 编辑器 | ✅(OIDC/SAML/LDAP/RADIUS,2026.8 过 OpenID 认证) | 双向(source + outpost 服务端) | Python+Go 多容器 + PG + Redis | ~24k ⭐ | 2025.2 起功能向 EE 倾斜;许可证策略由单一公司主导,曾反复 |
| **Casdoor** | Apache-2.0 | ✅ UI-first(用户/组织/应用/provider 全图形化) | ✅(OIDC/OAuth2/SAML/CAS) | 双向(含内置简易 LDAP 服务端) | Go 单二进制 + 一个 SQL 库,轻 | ~14k ⭐ | 文档参差;近期营销重心转向 AI 方向,传统 IAM 投入存疑;中文资料全(国内团队) |
| **Logto OSS** | MPL-2.0 | ✅ Console | ✅(核心定位) | 未见原生支持(未完全核实) | Node + PG | ~14k ⭐ | OSS vs Cloud 明确功能差(无协作邀请/内置邮件等);OSS 初始化仅 1 个管理员 |
| **Zitadel** | **AGPL-3.0(2025-03 v3 起,原 Apache)** | ✅ Console | ✅ | 无原生 | Go 单二进制 + PG | ~15k ⭐ | AGPL 内部自用无碍,对外提供服务触发 copyleft;商业化动作频繁 |
| **Authelia** | Apache-2.0 | ❌ **无用户管理 UI**(YAML 驱动) | ✅(4.39 起 GA,已过 OpenID 认证) | 仅作源 | Go 单二进制,<30MB RAM,最轻 | ~29k ⭐ | 增删用户靠文件或外部 LDAP;不适合"管理员不写配置管用户" |
| **LLDAP** | GPL-3.0 | ✅ 简洁(用户/组/改密) | ❌ 纯 LDAP | 即 LDAP 服务端 | Rust 单二进制 + SQLite,极轻 | ~6k ⭐ | 需搭配 Authelia/authentik 补 OIDC;schema 是非标子集 |
| **Kanidm** | MPL-2.0 | ✅ 内置 | ✅ + 只读 LDAP + RADIUS | 一体 | Rust 单服务 | ~5k ⭐ | 年轻;1.9 起升降级约束严格 |

**判断:** 若坚持"标准 OAuth + 有人味的管理界面",**Casdoor(UI-first、单二进制、许可证干净)和 Kanidm(单件一体)是唯二轻量选项**;Keycloak/authentik 功能最全但对"一个应用 + 几十~几百用户"属于用运维换用不到的能力(§6)。即便如此,相比 S1 仍多养一个有状态组件(库 + 升级 + CVE 跟踪)。

### S3-附.自建管理 UI vs 开源用户管理组件 —— 与 v4/OpenFGA 的对接面定量分析(2026-08-09 补)

问题:弃飞书后,用户管理界面自己写,还是引入功能强的开源用户管理组件"方便对接 OpenFGA"?

**关键事实:没有任何开源用户管理组件原生会写 OpenFGA tuple。** 引入外部组件后,v4 对接面一行不少 —— 仍要自建一座"IdP → tuple"同步桥(轮询/webhook 外部源 → add/remove tuple,≈ contact_sync v2),而它替你省掉的只是下表中最便宜的两行:

| 对接点 | 内容 | 现状 |
| --- | --- | --- |
| 登录 | 本地密码 → 签发**现有** session JWT | 机制已在,零改动 |
| 用户创建 | users 行(PK=UUID);OpenFGA subject = `user:<uuid>` | 表结构已在(ADR-0002 对冲设计) |
| 组 CRUD | 本地 groups 表 + 成员变更 → `group:<uuid>#member` tuple | `add_user_to_group` / `remove_user_from_group` 已在(`permissions.py:430`,现喂给飞书同步用,直接复用) |
| 项目/文件夹授权 UX | ProjectMembersDrawer / FolderGrantsPanel / SubjectPicker | **UI 与写 tuple 链路已在**;仅数据源切换(SubjectPicker 由飞书 API 改本地列表) |
| 离职/禁用 | `is_active=false` + `revoke_user_completely(subject)` | 已在,subject 是字符串、与来源无关 |
| GroupPicker 数据源 | 现代理飞书 contact API(`routers/groups.py:44`)→ 改查本地 groups 表 | 一个 endpoint 改写 |

结论:权限工作的大头(项目/文件夹授权 UX)无论如何都在本应用内且已建成;外部组件只能替代最容易的用户/组 CRUD 页面,却新增一个有状态服务 + 一座同步桥。**自建最小管理页(3~4 个 AntD 页面 + 一个薄 router, AdminAuditPage 有现成范式)是总工作量最小、语义最贴合 v4 的路线。** 外部组件只在"未来多系统统一 SSO"出现时重新值得 —— 届时经 OIDC 留口接入(S5),现在不为它预埋复杂度。

### S4. 换同类协作平台(钉钉/企业微信)

一句话排除:(官方/社区)钉钉回调规则与飞书同口径,换了不解决任何架构问题,只换了一家平台依赖;**企业微信可信域名明文不支持 IP 且需归属验证,纯内网直接不可用**。且 S4 隐含"客户组织在另一家平台上",与现状(已在飞书)矛盾。

### S5. 混合终态(推荐):本地账号基座 + 标准 OIDC 留口 + 飞书可选 connector

```
        ┌────────────────────────────────────────────┐
        │ material-storage                           │
        │  本地账号密码登录(基座,永远可用)          │
        │  标准 OIDC client(可配任意上游:飞书/     │
        │    Keycloak/Casdoor/IDaaS,0..N 个)       │
        │  应用内用户/组管理(权限的唯一写入口)      │
        └────────────────────────────────────────────┘
             ▲ 可选:飞书 connector(登录别名 + 通讯录导入 + IM 通知)
             ▲ 可选:未来客户有了 IdP,配 OIDC 即接入,零迁移
```

- 权限数据只引用内部 UUID(§3 解耦后),任何外部身份源的来去都不动权限。
- 飞书connector 在内网按 §1 的方式运行(redirect 登录 ✅、出站 API ✅、事件走长连接 ⚠️ 需 POC),业务验证有价值就留,没价值就关(`FEISHU_IM_ENABLED=false` 之类的开关已有先例,`settings.py:48-51`)。

## 6. "几十人单应用要不要上 IAM"的社区证据(佐证 S1/S5 倾向)

- (社区, skycloak 2026-07):"Keycloak 作为产品很少算 overkill,真正的负担是自托管带来的经常性运维(升级、CVE 补丁、HA)——让它显得'太多'的是 ops floor,不是软件本身。"
- (社区, unsubbed.co 2026-03):"Keycloak 是完整 Java 应用:600MB+ 镜像、空载 512MB 内存、配置面需数天理解。对 $10 VPS 上跑五个应用的团队是架构错配。"
- (社区, localtonet 2026-03):"单个应用只要登录注册,Keycloak 大概率超出所需;价值在多个应用共享账号会话、MFA、LDAP 免写代码时才显现。"
- (推断)映射本案:单应用、百人级、局域网、无专职 IdP 运维 —— 三条证据全部指向"应用内自建或最轻量件",全套 IAM 在"未来多个内部系统统一 SSO"出现时才值回成本(S5 的 OIDC 留口正是为那一刻准备的)。

| --- | --- | --- | --- |

## 8. 需要业务同事回答的问题(决策输入清单)

1. **公司日常协作实际跑在哪个 IM 上?飞书是"活着"还是"装着"?** —— 决定 2.2 全部价值是否真实存在。
   - **业务输入(2026-08-09,管理层):飞书是"装着"。** 团队日常 IM 实际是企业微信;飞书仅因本系统而被迫使用,反而增加一条办公沟通渠道成本。企业微信:第三方接入体验差,且(官方规则,§1)可信域名不支持 IP、需公网归属验证,纯内网不可集成。**结论:IM 集成整体放弃**(飞书 connector 与企业微信均不做),通知走应用内(+ 可选 SMTP)。
2. **入转调离是否在飞书里操作?** —— 决定"离职自动回收权限"是真实合规闭环还是理论能力;若否,自建体系的手动禁用 + 审计提醒是否可接受作为合规兜底?
   - **业务输入(2026-08-09,管理层):** 离职闭环优先级**降低** —— 局域网化后系统基本只对办公室内可达,已离职人员随物理/网络准入丧失而自然失去接触面。残留风险与配套判断见 §9 待办。
3. **审批体验底线在哪?** "IM 里点按钮" vs "收到邮件/系统内通知 → 打开系统审批",后者是否可接受?
4. **是否有外部/临时人员要进系统(外部合作方、短期访客)?** —— 飞书路线下这本就是缺口(外部联系人无 API,见 `feishu/research/contacts-as-identity-source.md` 缺口 1);自建体系下天然支持。若外部人员是常态,这一条反而偏向自建。
5. **公司有没有现成的 IdP / AD / LDAP / 统一登录?未来一年有没有其他内部系统要统一登录?** —— 决定 S2 是否直接成立、S3 是否值得养。
6. **有没有专职 IT 运维?** —— 决定 S3 的运维地板谁承担。
7. **登录方式偏好:** 接受"系统账号 + 密码"作为兜底吗(配合强制改密/密码策略)?
   - **业务输入(2026-08-09,管理层):接受,且明确用户名+密码为首选(不是兜底)** —— 用户为非技术人员,密钥类凭据(证书/令牌/免密链)有理解与支持成本,用户名密码沟通成本最低。设计推论(P1 实施遵循):用户名用好记形式(拼音/工号,不强制邮箱);session TTL 拉长(`session_jwt_ttl_seconds` env 可调,如 7~30d),配合浏览器记住密码,重复输入频率极低;忘密码走管理员重置,不依赖邮件通道。
   - **技术注(同期澄清):** IP 不能作应用层身份依据(DHCP 漂移 + 多人共机 + 权限/审计需要具名 actor);内网 subnet 准入是网络层补充,不替代应用层身份。
